# 微信小游戏自动游玩客户端（天天军棋·翻翻棋）

> 目标游戏：腾讯天天军棋（微信小游戏）· 翻翻棋。用户手动打开游戏主界面，客户端检测窗口、点击“翻翻棋”、进入对局；Create ML 负责感知，Python + MLX 训练，MLX Swift 推理。
> 本文是可行性评估 + v1 架构与项目组织，不是最终 API 设计。基于 2026-10-22/23 本机实测与决策。

## 结论

技术路线定为：

**Swift 单窗口客户端 + ScreenCaptureKit 捕获 + Vision/Create ML/Core ML 感知 + CGEvent 输入；Python + MLX 负责训练（含翻翻棋规则引擎与模拟器）；MLX Swift 负责推理；模型与数据不打包进 App。**

六个关键判断：

1. **只做腾讯天天军棋的翻翻棋，不做平台、不做多游戏。** 一个客户端只服务这一款游戏、这一个模式。
2. **用户辅助启动，不自动打开微信。** 用户自己进入天天军棋主界面；客户端只负责检测窗口、点“翻翻棋”、处理弹窗、进入牌局。之前设计的“发现 → 游戏 → 搜索”整条链路删除。
3. **Create ML 做感知，Python + MLX 训练，MLX Swift 推理。** 感知模型输出 Core ML；策略训练在 Python；客户端进程内用 MLX Swift 加载 `safetensors`，运行时不需要 Python。
4. **翻翻棋是部分可观测棋类，值得做规则引擎/模拟器。** 真实对局用于采集和评测；批量训练靠模拟器自博弈，否则样本成本太高。
5. **只保留一个 GUI 主窗口，不做菜单栏 App / 状态栏图标。** 授权、校准、训练、日志都在主窗口内完成。
6. **最大风险是棋盘感知、规则一致性、匹配流程和合规，不是框架。** 翻翻棋有随机暗子，不能承诺必胜，只能追求期望胜率和决策质量。

### 可行性评分

| 能力 | 评级 | 判断 |
|---|:---:|---|
| 识别游戏窗口 | ★★★★★ | `WeChatAppEx` 独立窗口，ScreenCaptureKit 可稳定捕获 |
| 识别主界面/翻翻棋入口 | ★★★★☆ | OCR + 模板 + 校准锚点；入口清楚时可靠 |
| 棋盘格点/棋子识别 | ★★★☆☆ | 棋盘固定、格子小；需要校准 + 分类器 + 时序平滑 |
| 规则引擎/模拟器 | ★★★★☆ | 规则固定、状态空间小；部分可观测需要额外处理 |
| Python MLX 训练 | ★★★★☆ | 小模型在 M1 Pro 上训练快；生态够用 |
| MLX Swift 推理 | ★★★★☆ | 直接加载 safetensors；需与 Python 做数值一致性测试 |
| 真实对局自动操作 | ★★★☆☆ | 匹配、动画、计时器、弹窗都可能打断 |
| 从零在线 RL（真实游戏） | ★☆☆☆☆ | 真实对局太慢，且会影响真人玩家；不做 |
| 合规 | ★☆☆☆☆ | 违反微信/游戏协议，封号与分发风险高 |

## 1. 目标与边界

### 产品定位

一款游戏一个客户端：腾讯天天军棋的翻翻棋模式。用户负责打开游戏主界面；客户端负责从主界面进入翻翻棋、感知棋盘、自动对局、采集数据、周期性训练，并在评测通过后替换模型。

翻翻棋开局暗子随机，存在运气成分。目标不是“必胜”，而是：

- 稳定完成“检测窗口 → 进入翻翻棋 → 下完一局”的闭环。
- 在固定评测集上，新模型的期望胜率/决策质量不低于当前基线。
- 能自己反复玩、周期性变强，而不是每一步都在线学习。

### 用户流程

1. 用户打开微信，进入腾讯天天军棋主界面（已登录、公告已处理）。
2. 用户打开本客户端。
3. 客户端检测游戏窗口，确认当前是天天军棋主界面。
4. 客户端点击“翻翻棋”。
5. 客户端处理规则/公告/更新弹窗；按配置选择人机练习或快速匹配。
6. 进入牌局，AI 自动对局；同时采集状态、动作和结果。
7. 一局结束：人机练习可自动“再来一局”；真人匹配默认停下，等待用户确认。
8. 周期训练后，固定评测集通过才晋级；失败回滚。

### v1 范围

- 只支持腾讯天天军棋、翻翻棋模式、一个微信账号、一个游戏窗口。
- 只支持 macOS 27+、Apple Silicon、微信 4.1.x；版本不匹配时提示重新校准。
- 默认按微信小游戏（`WeChatAppEx`）设计；如果是独立 Mac 客户端，只替换窗口匹配配置，流程不变。
- 用户手动打开游戏主界面；客户端不启动微信、不点“发现”、不搜索小程序。
- 感知：Create ML 屏幕状态/棋子分类 + Vision OCR/模板匹配 + 棋盘格点校准。
- 训练：Python + MLX；包含翻翻棋规则引擎、模拟器、行为克隆、DAgger、自博弈。
- 推理：MLX Swift，运行时不需要 Python。
- 训练进程由客户端按需启动，结束即退出；不做常驻 Python 服务。
- 只保留一个 GUI 主窗口，不做菜单栏 App。
- 全部本地运行，无云端训练、无遥测、无账号体系。

### 非目标

- 自动打开微信、自动点“发现”、自动搜索小程序、自动登录。
- 多游戏平台、项目管理系统、任务队列、多用户/云端训练。
- 在真实游戏上从零做在线 RL、大规模真人匹配自博弈。
- 修改微信/游戏客户端、读进程内存、劫持网络、注入 dylib。
- 多账号、多实例并发。
- 绕过实名认证、防沉迷、反作弊。
- Mac App Store 分发。
- Windows / iOS 版本。
- 保证战胜真人或内置 AI。

### 成功指标

- 游戏窗口识别成功率 > 95%。
- 主界面识别 + 点击“翻翻棋”成功率 > 95%。
- 棋盘格点识别成功率 > 98%，棋子分类在已校准皮肤上 > 99%。
- 从点击“进入翻翻棋”到可操作牌局 < 15 秒（不含匹配等待）。
- 连续运行 2 小时无人工干预；异常能暂停并交还鼠标。
- 模拟器固定种子评测中，新模型胜率显著高于启发式基线；真机评测不低于当前版本。

## 2. 本机实测与游戏事实

- 开发环境：macOS 27.0.1、Apple M1 Pro、Xcode 27.1、Swift 6.4。
- 微信版本：4.1.15（bundle id `com.tencent.xinWeChat`）。
- 小程序由独立进程 `WeChatAppEx` 渲染，bundle id `com.tencent.flue.WeChatAppEx`，使用 Chromium/Mojo 架构，带 GPU、Renderer、Network 等 helper 进程，**不是主微信进程**。
- 游戏正文区域几乎不暴露 AX 节点；棋盘、按钮、弹窗都必须靠视觉识别，不能假设有可访问性树。
- 主微信注册了 `weixin://`、`wechat://`、`xweixin://` 三个 URL scheme；`WeChatAppEx` 没有注册 scheme。本方案不需要深链，因为用户会手动打开游戏。
- `CGEventPostToPid` 不在公开 SDK 头文件中，不能作为正式方案；只能走全局 HID 事件注入。

> [!note] 翻翻棋规则以游戏内为准
> 公开资料里的“军棋翻翻棋”常见为 4×8 棋盘、32 枚暗子、两人对战，目标是吃光对方可移动棋子或扛走军旗。天天军棋的版本、皮肤、棋子集合可能不同；实现前必须用游戏内规则页 + 20–50 局回放校准 `rows/cols`、棋子集合、军衔顺序、炸弹/地雷规则和胜负条件。**不要硬编码 4×8。**

> [!tip] 优先人机练习
> 公开资料显示天天军棋有 AI 陪练/人机模式。微信小游戏版本是否保留、入口在哪，需要实测。若可用，训练和评测优先走人机练习；真人匹配默认关闭，避免影响其他玩家和放大合规风险。

## 3. 启动与主窗口

### 3.1 检测游戏窗口

不再检测“微信是否登录、是否能点发现”。只关心游戏窗口：

| 状态 | 判断方式 | 引导 |
|---|---|---|
| 微信未运行 | `com.tencent.xinWeChat` 不在运行进程列表 | “请先打开微信并进入天天军棋” |
| 游戏窗口未开 | 没有 owner 为 `WeChatAppEx` 的窗口 | “请在微信中打开天天军棋主界面” |
| 窗口在但主界面未识别 | 截图分类不是 `main`，OCR 也没有“翻翻棋” | “请停留在天天军棋主界面” |
| 主界面已识别 | 屏幕分类为 `main` + OCR/模板命中“翻翻棋” | 就绪，可进入翻翻棋 |
| 已在牌局 | 屏幕分类为 `board`，检测到棋盘格点 | 提供“继续/结束/等待” |
| 结算/弹窗 | 屏幕分类为 `result` / `popup` | 按规则处理或暂停 |

实现要点：

- 用 `NSWorkspace` 监听微信启动/退出；用 `CGWindowListCopyWindowInfo` 或 `SCShareableContent` 找 `WeChatAppEx` 窗口。
- 窗口标题可能为空；不要只靠标题。用 owner + 尺寸 + 截图分类综合判断。
- 有多个 `WeChatAppEx` 窗口时，逐个截图做屏幕分类；命中主界面的那个优先；仍不唯一就让用户选一次。
- 独立客户端：把 `WindowMatch` 的 owner/bundle 换成游戏进程即可，后续流程不变。
- 权限检查放在最前面：屏幕录制、辅助功能、输入监控，缺一个后面都会以难以定位的方式失败。
- **不自动启动微信**。窗口没开就提示用户，提供“重新检测”按钮。

### 3.2 单窗口主界面

不再有“项目列表”。一个客户端只服务天天军棋/翻翻棋，**只有一个主窗口，不做菜单栏 App / 状态栏图标**；授权、校准、训练、日志都在这个窗口内切换。

```text
┌ 天天军棋 · 翻翻棋 AI ───────────────────────┐
│ [ 概览 ] [ 训练 ] [ 日志 ] [ 设置 ]          │
│ 游戏窗口：已检测   主界面：已识别  ● 就绪    │
│ 模式：翻翻棋       对手：人机练习             │
│ 模型：v3  模拟器胜率 68%  真机胜率 54%       │
│ 当前：等待进入 / 第 12 局 / 训练中            │
│                                              │
│ [ 进入翻翻棋 ] [ 自动对局 ] [ 暂停 ] [ 急停 ]│
└──────────────────────────────────────────────┘
```

主窗口固定四个页面：**概览、训练、日志、设置**；设置页放权限、校准、棋盘配置、对手模式和模型路径。授权、校准、日志都用主窗口里的页面或 sheet，不另开窗口。关闭主窗口即退出应用，不驻留菜单栏；训练中关闭需确认，退出时终止训练子进程。概览页内嵌游戏画面的竖屏克隆视图（只读，见 3.6），作为人工监控与 HUD 的实时画面载体。

运行状态机：

```text
idle            空闲
waitingWindow   等待游戏窗口
verifying       识别主界面/当前界面
enteringMode    点击“翻翻棋”
matching        等待匹配/对手
ready           牌局已就绪
playing         AI 自动对局
recording       录制人类示范
training        Python MLX 训练中
evaluating      固定评测集评测
paused          暂停，交还鼠标
failed          失败，保留截图/日志
```

模型与数据存储：

```text
~/Library/Application Support/TianTianJunqiAI/
  game-profile.json          # 游戏名、模式、窗口匹配、棋盘规格、奖励规则
  calibration.json           # 窗口、画布 ROI、棋盘四角、入口/按钮锚点、模板
  episodes/<episode_id>/
    meta.json
    states.jsonl
    actions.jsonl
    reward.json
    frames/                  # 关键帧/失败帧，不存全部原始帧
  datasets/<hash>/
    manifest.json
    train.jsonl
    eval.jsonl
  models/v1/
    model.safetensors        # MLX 策略/价值权重
    model.json               # 网络结构
    manifest.json            # 指标、数据集哈希、版本
  perception/
    screen_state.mlmodel     # 主界面/牌局/结算/弹窗
    cell_classifier.mlmodel  # 棋子格分类
  sim/
    rules.json               # 规则版本
    seeds/                   # 评测种子
  logs/
```

三个细节：

- 策略模型不打包进 App；启动时按 manifest 加载，版本不匹配就标 `stale`，要求重校准或重训。
- Core ML 感知模型首次加载会编译；启动时后台预热，避免第一步卡顿。
- 单实例锁：同一时间只允许一个客户端控制游戏窗口和鼠标。

### 3.3 预检

点击“进入翻翻棋”“自动对局”或“开始训练”之前，先跑 Preflight：

- 微信已运行，游戏窗口存在。
- 屏幕录制、辅助功能、输入监控权限齐全。
- 主界面已识别，或当前已在牌局（允许继续）。
- 校准存在且未过期；棋盘规格与当前游戏/皮肤一致。
- 自动对局时模型存在且兼容；首次训练允许没有模型，先录制示范。
- 训练时 Python/uv 环境可用；缺环境只禁用训练，不影响加载已有模型游玩。
- 磁盘空间足够（回合数据可能到 GB 级）。
- 没有未知弹窗；有弹窗先按模板关闭，关不掉就暂停。

如果检测到当前已经在牌局里，**不要再点“翻翻棋”**；直接进入 `playing` 或让用户选择“继续/结束/等待”。

### 3.4 进入翻翻棋

不要写成一串 `sleep + click`，而是“可验证的步骤引擎”：

```swift
struct EntryStep {
    let action: Action          // activate / click / tapButton / wait
    let predicate: Predicate    // 怎样算成功
    let timeout: Duration
    let retries: Int
}
```

进入路径：

| # | 步骤 | 实现 | 成功判据 | 超时 |
|---|---|---|---|---|
| 1 | 激活游戏窗口 | `NSRunningApplication.activate` + 窗口 raise | 窗口 frontmost | 3s |
| 2 | 确认主界面 | 屏幕分类 + OCR/模板“翻翻棋” | 分类为 `main`，入口命中 | 5s |
| 3 | 点击“翻翻棋” | OCR 包围盒中心 / 模板 / 校准锚点 | 进入模式页或匹配页 | 3s |
| 4 | 清理弹窗 | 公告、规则、更新、签到 | 屏幕稳定，无未知弹窗 | 10s |
| 5 | 选择对手模式 | 人机练习 / 快速匹配 / 好友房 | 进入匹配或直接开局 | 5s |
| 6 | 开始匹配/开局 | 点击“开始”“快速匹配”“人机对战” | 出现等待/棋盘 | 5s |
| 7 | 等待牌局 | 检测棋盘四角 + 格点 + 棋子 | 棋盘稳定，轮次可见 | 20s |
| 8 | 开局清理 | 规则/提示/广告/断线弹窗 | 棋盘 ROI 稳定 | 15s |
| 9 | 就绪 | 轮次/计时器可读 | 进入 `playing` | 5s |

关键实现：

- **主界面识别**：屏幕分类器先判断 `main`；OCR 找“翻翻棋”。OCR 命中多个时，优先模式区里面积最大的；仍不确定就暂停，让用户点一次并记录位置。
- **入口点击**：优先 OCR 包围盒中心；其次模板匹配；最后用校准锚点。三种方式都失败就暂停，不要乱点。
- **校准向导**：第一次使用时，让用户在主窗口里框选“翻翻棋”入口、棋盘四角、关键按钮（开始/再来一局/关闭弹窗）。存归一化坐标，不存绝对屏幕坐标。
- **棋盘规格**：`BoardSpec.rows/cols` 从 `game-profile.json` 读取；公开资料常见 4×8，但必须实测确认，不能写死。
- **已在牌局**：如果第 2 步已经识别到 `board`，跳过 3–6，直接进入 `playing`。
- **匹配等待**：匹配可能很久；设总超时和取消按钮，不要重复点击“开始匹配”造成排队异常。
- **对手模式**：默认 `aiPractice`；没有入口时回退 `quickMatch`，并在 UI 明确提示“将进入真人匹配”。真人匹配默认不自动连开。
- **窗口标题为空**：用 owner + 尺寸 + 截图分类；标题只作为加分项。
- **不需要中文输入/搜索**：原方案里的 Unicode 输入、图标匹配、搜索结果匹配全部删除。

失败回退：

1. 模式页没出来：回主界面，重新识别“翻翻棋”。
2. 入口点了没反应：换 OCR/模板/锚点，最多 2 次；仍失败就暂停。
3. 未知弹窗：截图，暂停，交给用户。
4. 游戏更新/皮肤变化：要求重新校准，不要硬点。

### 3.5 对局与训练闭环

```text
进入翻翻棋
  ↓
MLX Swift 策略推理
  ↓
CGEvent 点击格子/按钮
  ↓
棋盘状态更新 + 奖励
  ↓
回合结束
  ↓
Episode 落盘
  ↓
模拟器自博弈 / Python + MLX 训练
  ↓
固定评测集：通过 → 晋级；失败 → 回滚
  ↓
热替换策略快照
```

**采集**

- 棋盘游戏不需要 60fps 全量录制；按 2–5fps 采样，状态变化/落子/翻牌时额外抓关键帧。
- 每局记录：`meta.json`、`states.jsonl`、`actions.jsonl`、`reward.json`；关键帧放 `frames/`。
- 人类示范用 `CGEventTap`（listen-only）抓鼠标事件；AI 对局直接记录策略输出。
- 记录轮次、计时器、选中格、最后一步、结果；这些是复盘和规则校验的关键。

**训练**

- 真实对局数据用于行为克隆、DAgger 和真机评测；批量自博弈在 Python 模拟器里跑。
- 行为克隆起步：人类示范 10–20 局，覆盖翻牌、吃子、护旗、残局。
- 自动对局后进入 DAgger：AI 玩，失败局面人工纠正，纠正样本入数据集。
- 模拟器稳定后，再上 PPO/自博弈/MCTS；不要一上来就在真实游戏上做在线 RL。
- 训练由 Python MLX 在后台进程执行；Swift 持有冻结快照，评测通过后才热替换。

**评测与晋级**

- 模拟器固定种子 + 固定启发式对手，跑 N 局，记录胜率、平均步数、非法动作率。
- 真机固定开局/固定皮肤，跑 N 局，记录胜率、完成率、异常中断。
- 新模型必须超过当前基线才晋级；翻翻棋有随机性，用置信区间，不要只看一两局。
- 每次晋级保存 `model.safetensors` + `model.json` + `manifest.json`，支持回滚。

**游玩**

- 棋盘游戏控制频率 2–5Hz 足够；落子动画/确认阶段可以降到 1Hz。
- HUD 显示状态、FPS、推理耗时、当前模型版本、当前对手模式；实时画面由概览页竖屏克隆视图承载（见 3.6）。
- 安全阈值：单局最长时长、连续失败次数、非法动作次数、匹配超时 → 自动停止并截图。
- 提供“暂停并交还鼠标”，避免用户想接管时和机器人抢鼠标。

### 3.6 画面克隆视图（只读竖屏监控）

背景：微信小游戏在 macOS 上无法把横屏窗口转成竖屏，而翻翻棋棋盘天然适合竖屏观看。客户端在概览页内嵌游戏画面的**竖屏克隆视图**，作为人工监控与 HUD 的实时画面载体。

- **画面源复用**：克隆视图是 CaptureService（SCStream）同一帧流的第二个消费者，不新增采集成本；显示帧率独立于感知的 2–5fps 采样。
- **变换模式由实测决定**（对应开发计划 P0-1）：

| 窗口内容形态 | 处理方式 |
|---|---|
| 竖版画布居中、左右留黑边 | 按 `canvasROI` 裁剪直接显示，无需旋转 |
| 强制横版渲染铺满窗口 | 旋转 90° 显示（文字侧躺，需确认可接受） |
| 窗口可 resize 且游戏自适应 | 直接把窗口拖成竖屏比例，可能无需克隆视图 |

- **只读边界**：克隆视图不提供输入映射，不能替代真实窗口；§9.1“游戏窗口必须可见且前台”的注入约束不变。未来若要“点克隆画面操作真窗口”，需另做坐标映射层与防自遮挡，放到人工接管阶段。
- **变换仅限显示层**：感知、校准、CGEvent 全部继续使用原始窗口坐标系，避免两套坐标互相污染。

## 4. 应用状态机

```text
启动
├─ 权限检查
│  └─ 缺权限 → 权限引导（主窗口内）
├─ 游戏窗口检查
│  ├─ 微信未运行 → “请先打开微信”
│  ├─ 游戏窗口未开 → “请打开天天军棋主界面”
│  ├─ 窗口在但主界面未识别 → “请停留在主界面”
│  └─ 主界面已识别 → 就绪
主窗口
├─ 未校准 → 校准向导（主窗口内）
├─ 已校准 → 就绪
└─ 就绪
   ├─ 进入翻翻棋 → 匹配 → 牌局
   ├─ 录制示范 → 数据集
   ├─ 自动对局 → 采集 → 训练 → 评测 → 晋级/回滚
   └─ 自动游玩 → 暂停/结束/异常
```

`GameSession` 五种模式共用同一套窗口、捕获、感知、注入逻辑：

| 模式 | 谁在操作 | 产出 |
|---|---|---|
| `enter` | 客户端 | 从主界面进入翻翻棋 |
| `record` | 人 | 示范回合、训练数据 |
| `collect` | 模型 | 自动对局、困难样本 |
| `evaluate` | 模型 | 评测指标、失败分类 |
| `play` | 模型 + HUD | 实时游玩、人工接管 |

同一时间只允许一个 Session 持有游戏运行时租约；训练任务可以在后台运行，但运行时要串行。

```swift
    var ownerName: String          // "WeChatAppEx"

    var buttons: [String: CGRect]  // 开始/再来一局/关闭
    var templates: [String: URL]
    var theme: String
}

struct Episode {
    var id: String
    var mode: String               // "翻翻棋"
    var startedAt: Date

    var score: Int
}

struct ModelVersion {
    var id: String
    var weightsURL: URL            // model.safetensors
    var architectureURL: URL       // model.json
    var manifest: ModelManifest
}

struct ModelManifest {
    var modelVersion: Int
    var perceptionVersion: String
    var gameVersion: String?
    var datasetHash: String
    var metrics: [String: Double]
    var createdAt: Date
}
```

存储原则：

- 一款游戏一个 `game-profile.json`；校准文件只存本机，不入库。
- 数据集、模型、日志全部放 Application Support，不进 App Bundle。
- 删除数据时一并删除 episodes/datasets/models，避免磁盘泄漏。
- 录制内容可能包含昵称、头像、聊天信息，默认只存本地，提供一键删除和空间统计。
- 每个模型必须能追溯到“数据集哈希 + 感知版本 + 游戏版本 + 训练配置”。
- Swift 启动时读 `models/<version>/manifest.json`，用 MLX Swift 加载 `model.safetensors` + `model.json`；不需要 Python。

### 7.3 契约与训练协议

先定义四个结构：`GameState`、`Action`、`Episode`、`ModelManifest`。其中 `GameState` / `Action` 用于回合录制和 MLX 特征输入；**推理在 Swift 进程内完成，不存在逐动作 RPC**。

```json
// GameState
{
  "schema": 1,
  "phase": "playing",
  "board": {
    "rows": 4,
    "cols": 8,
    "cells": [
      {"i": 0, "state": "hidden"},
      {"i": 1, "state": "empty"},
      {"i": 2, "state": "revealed", "color": "red", "piece": "che", "confidence": 0.98}
    ]
  },
  "turn": "red",
  "selected": null,
  "legal_actions": [3, 4, 5, 18],
  "timers": {"me": 12.3, "opponent": 13.1},
  "last_move": {"from": 10, "to": 18}
}
```

```json
// Action
{"type": "tap_cell", "cell": 18}
{"type": "tap_button", "name": "start"}
{"type": "wait", "ms": 300}
```

坐标一律归一化到画布 ROI，0..1，避免分辨率和 Retina 问题；`cell` 是 `0..rows*cols-1` 的棋盘格索引。

训练进程用 **Process + stdout JSONL**，不设常驻服务：

| 事件 | 方向 | 说明 |
|---|---|---|
| `train.start` | Swift → Python | 命令行参数：config、episodes、out |
| `progress` | Python → Swift | stdout JSONL：phase / episode / loss / metric |
| `done` | Python → Swift | exit 0；写 `manifest.json` |
| `error` | Python → Swift | stderr + 非 0 exit |
| `cancel` | Swift → Python | SIGTERM |

细节：

- `stdout` 只写 JSONL，日志走 stderr 或文件，避免 UI 解析混乱。
- 每行带 `schema` 版本；Swift 按行解码，未知字段忽略。
- 训练产物写到 `models/<version>/`；完成后由 MLX Swift 加载并做 smoke test。
- 取消用 `Process.terminate()`，10 秒后 `SIGKILL`；不要留孤儿进程。
- **不要把原始帧塞进 JSON**；episode 里用 `frame_ref` 引用关键帧。
- 推理是进程内同步调用，不存在逐动作 RPC，也没有 `act/action` 超时。

### 7.4 唯一部署形态

| 场景 | 需要 Python | 说明 |
|---|---|---|
| 自动游玩 / 在线评测 | 否 | MLX Swift 加载 `safetensors`，进程内推理 |
| 训练 / 导出 | 是 | 本地 `uv` 环境；也可在另一台 Mac 训练后拷贝模型 |
| 离线/模拟器评测 | 是 | `wgai.cli eval`，不控制游戏窗口 |
| 对外分发 | 否 | App 不依赖 Python 运行时 |

要点：

1. **推理不跨进程。** Swift 直接加载 `model.safetensors` + `model.json`，不启动 Python 推理服务。
2. **Python 只是训练工具。** 训练进程由 `TrainerBridge` 启动，结束即退出；App 不依赖它常驻。
3. **模型结构只维护一份。** `model.json` 由 Python 导出，Swift 按同一份配置重建网络；固定输入做输出一致性测试。
4. **没有 Python 也能玩。** 只训练按钮禁用并提示安装训练环境；已训练模型可正常加载。
5. **训练可以离线。** 训练不要求游戏窗口在前台；只有采集/真机评测需要运行时。

### 7.7 工作流

```makefile
bootstrap:   # uv sync + xcodebuild
record:      # 启动 App，进入录制模式
train:       # uv run python -m wgai.cli train --config configs/bc.yaml --out data/models/v4
export:      # 可选：train 已写出 model.safetensors / model.json / manifest.json
eval:        # 模拟器评测 + Swift MLX 真机评测
play:        # App 用 MLX Swift 加载最新模型
test:        # Swift 单测 + Python 单测 + schema/规则校验
```

CI 里至少跑五类测试：

1. **schema 契约**：Swift 编码的 `GameState` 能被 Python 解码，反之亦然。
2. **规则单测**：军衔比较、炸弹/地雷、翻牌、移动、胜负条件；用真实回放校验模拟器。
3. **过拟合测试**：用 10 条样本训练，loss 必须能降到接近 0，证明训练链路没断。
4. **推理一致性（必须）**：同一份 `model.safetensors` + `model.json`，Python 与 MLX Swift 对固定输入的输出一致（容差 1e-4）。
5. **模型加载 smoke test**：App 能加载新模型并跑 10 步不崩。

## 8. 翻翻棋 AI 设计

### 8.1 游戏建模

翻翻棋是**部分可观测 + 随机开局**的两人棋类：

- 开局棋子背面朝上、位置随机；玩家不知道未翻开的棋子身份。
- 翻牌后才知道颜色和军衔；吃子结果取决于双方军衔、炸弹、地雷等规则。
- 胜负通常取决于吃掉对方军旗或让对方失去可移动棋子；具体以游戏内规则为准。

因此状态不能只存“画面”，还要存：

- 棋盘可见状态：空格、暗子、已翻开的颜色/棋子。
- 已吃掉的棋子、双方剩余棋子集合。
- 轮次、计时器、最后一步、选中格。
- 对暗子的信念（belief）：根据已翻开的棋子和已吃棋子，推断剩余暗子的可能分布。

**不要把它当完全信息棋**。如果只按可见棋盘训练，模型会低估暗子风险。

### 8.2 感知

| 感知任务 | 方案 | 输出 |
|---|---|---|
| 屏幕状态 | Create ML 图像分类 | `main` / `modeLobby` / `matching` / `board` / `result` / `popup` / `unknown` |
| “翻翻棋”入口 | Vision OCR + 模板 + 校准锚点 | 入口包围盒/中心点 |
| 棋盘四角 | Vision 矩形检测 + 校准 + 模板 | 归一化四角 |
| 棋子格 | 棋盘透视变换 + Create ML 棋子分类 | `empty` / `hidden` / `revealed(red/black, piece)` |
| 文字/计时 | Vision OCR（局部 ROI） | 轮次、倒计时、结果、按钮文字 |
| 按钮 | OCR/模板/校准 | 开始、匹配、再来一局、关闭 |

实现要点：

- 棋盘格点先做透视变换到标准矩形，再按 `rows × cols` 切格；每格单独分类，比整盘目标检测更稳。
- 棋子分类器先分 `empty/hidden/revealed`，再分颜色和军衔；类别多时拆成两级模型。
- 隐藏棋子不要猜身份；只输出 `hidden`，把身份留给信念模块。
- 动画期间（翻牌、吃子、移动）暂停分类，等画面稳定 2–3 帧再更新状态。
- 每个输出带置信度；低置信度时暂停或让用户确认一次，不要硬猜。
- 皮肤/主题变化会破坏模板和分类器；校准文件记录 `theme`，不匹配就要求重新校准。

### 8.3 动作空间

棋盘游戏动作很小，适合离散策略：

```text
tap_cell(i)         i = 0..rows*cols-1，翻牌/选中/落子
tap_button(name)    start / again / close / confirm
wait(ms)            等待动画/对手
```

- 一次点击算一个 action；翻牌是“点暗子”，移动是“点己方棋子 → 点目标格”。
- `GameState.legal_actions` 由规则引擎/感知给出；模型输出非法动作时，用合法掩码兜底。
- 如果棋盘不是 4×8，动作空间随 `rows*cols` 变化，不写死。

### 8.4 规则引擎与模拟器

这是翻翻棋 AI 的核心增量。真实对局一小时只能跑几十局，模拟器一小时可以跑几千到几万局。

`sim/` 组成：

```text
sim/
├─ board.py       # 棋盘、格子、暗子分布
├─ rules.py       # 军衔、炸弹、地雷、移动、吃子、胜负
├─ engine.py      # 状态推进、合法动作、随机暗子
├─ belief.py      # 暗子信念/确定性采样
└─ selfplay.py    # 自博弈、对手池、课程学习
```

要求：

- 规则引擎与游戏内规则逐条对齐；用真实回放做回归测试。
- 支持固定种子，评测可复现。
- 支持“确定性采样”：从未知暗子集合里采样若干完整局面，分别搜索/评估，再综合动作。
- 模拟器只服务翻翻棋，不做通用游戏引擎。
- 规则版本写进 `rules.json`；规则改了，旧模型和数据集要标记不兼容。

> [!warning] 规则不一致比模型弱更致命
> 如果模拟器里的军衔、炸弹、地雷、胜负条件和游戏不一致，自博弈会学到错误策略，真机表现会崩。第一版必须先用真实回放把规则引擎校准，再大规模训练。

### 8.5 训练路线

**V1：行为克隆 + 合法掩码 + 启发式**

- 人类示范 10–20 局，覆盖翻牌、吃子、护旗、残局。
- 监督学习“状态 → 动作”；用合法动作掩码过滤非法输出。
- 启发式基线：优先翻暗子、按军衔吃子、保护军旗、避免送子。
- 目标：先跑通“能下完一局”，不追求强。

**V2：模拟器自博弈**

- 用规则引擎生成对局；策略网络 + 价值网络；PPO 或 AlphaZero 风格 MCTS。
- 部分可观测：每步采样若干暗子确定性局面，做搜索/评估；或把信念特征直接输入网络。
- 对手池：随机、启发式、历史模型；避免只赢一个对手。
- 课程学习：先学翻牌/吃子，再学残局/护旗。

**V3：DAgger + 真机微调**

- AI 在真实游戏玩，失败局面人工纠正；纠正样本入数据集。
- 真机数据只做微调和评测，不做大规模在线 RL。
- 每次训练后在模拟器固定种子 + 真机固定评测集上评估；通过才晋级。

奖励建议：

- 胜 +1，负 −1，平/超时 0。
- 吃子按棋子价值给少量 shaping；非法动作/超时给惩罚。
- 不要过度 shaping，避免模型只会吃子不会赢棋。

### 8.6 模型格式与部署

```json
// model.json：只描述网络结构
{
  "schema": 1,
  "architecture": "cnn_policy_value",
  "input": {"rows": 4, "cols": 8, "channels": 18},
  "trunk": [64, 64],
  "heads": {"policy": "cells", "value": 1}
}
```

```json
// manifest.json：记录来源、指标、版本
{
  "modelVersion": 3,
  "modelFile": "model.safetensors",
  "architectureFile": "model.json",
  "rulesVersion": "fanfanqi-1",
  "perceptionVersion": "p3",
  "gameVersion": "1.2.3",
  "datasetHash": "sha256:...",
  "metrics": {"simWinRate": 0.68, "realWinRate": 0.54},
  "createdAt": "2026-10-23T10:30:00+08:00"
}
```

- 权重用 `safetensors`：Python 训练导出，MLX Swift 推理加载。
- `model.json` 只描述层结构，两端按同一份配置重建网络；`manifest.json` 记录指标、规则版本、数据集哈希。
- **推理固定用 MLX Swift**，Python 不提供运行时推理；MLX 没有官方 Core ML 导出，本项目也不需要。
- Core ML 感知模型用 `MLModel.compileModel(at:)` 预编译并预热。

### 8.7 性能预算（M1 Pro）

| 阶段 | 预算 |
|---|---|
| ScreenCaptureKit 捕获 30–60fps | 5–10% CPU |
| Vision OCR（局部 ROI） | 10–30ms |
| Create ML 屏幕分类 | 2–5ms |
| 棋子格分类（32 格批量） | 3–10ms |
| MLX Swift 策略推理（结构化状态） | 2–5ms |
| 决策 + CGEvent | 2–3ms |
| 端到端（感知 → 动作） | 50–200ms |
| 决策频率 | 2–5Hz（棋盘游戏足够） |

翻翻棋有计时器，200ms 以内完成一步很安全；不需要 30Hz 的控制循环。

### 8.8 评测与晋级

- 模拟器：固定种子 + 随机/启发式/历史模型三类对手，各跑 N 局；记录胜率、平均步数、非法动作率、超时率。
- 真机：固定皮肤、固定对手模式，跑 N 局；记录胜率、完成率、异常中断、平均每步耗时。
- 翻翻棋随机性大：用置信区间/多日评测，不要用一两局定胜负。
- 晋级门禁：模拟器胜率不低于基线，真机胜率不低于基线，非法动作率不升高；否则回滚。
- 保留失败录像和状态快照，用于复盘和规则校验。

## 9. 关键实现细节

### 9.1 窗口激活与捕获

- 用 `NSRunningApplication.activate(options: .activateIgnoringOtherApps)` 激活微信/游戏窗口；必要时 AX raise 主窗口。
- 用 `SCShareableContent` 找 `WeChatAppEx` 窗口；窗口标题为空时用 owner + 尺寸 + 截图分类。
- 游戏窗口必须可见且前台；不做后台/隐藏窗口的 CGEvent 注入。
- 窗口尺寸变化、缩放、多显示器都会影响坐标；每次会话开始重新校验 `windowSize` 和 `canvasROI`。

### 9.2 坐标换算

- `CGWindowList` / AX 的窗口 bounds 是 point；ScreenCaptureKit 的帧是 pixel。
- `scale = 帧宽 / bounds 宽`，点击坐标要按 scale 换算。
- CGEvent 使用全局显示坐标，原点在主屏左上角；AX 使用屏幕坐标，注意多显示器偏移。
- 校准存归一化坐标（0..1），相对窗口内容区，不存绝对屏幕坐标。
- 棋盘四角也要归一化；透视变换后再切格，避免窗口缩放/棋盘缩放导致错位。

### 9.3 主界面与入口识别

- 屏幕分类器先判断 `main`；OCR 找“翻翻棋”三个字。
- OCR 命中多个时：优先模式区/按钮形状的候选；面积最大的优先；仍不确定就暂停让用户点一次。
- 模板匹配作为 OCR 的补充；皮肤变化时模板失效，重新校准。
- 校准锚点是最后兜底；每次点击后用“进入模式页/匹配页”验证，不假设点击成功。
- 点击“翻翻棋”后等待 0.5–1 秒再截图；动画期间不要连续点击。

### 9.4 棋盘状态感知

- 棋盘四角 → 透视变换 → 标准矩形 → 按 `rows/cols` 切格。
- 每格分类：`empty` / `hidden` / `revealed`；`revealed` 再分颜色和军衔。
- 用连续帧投票/平滑：同一格连续 2–3 帧一致才更新；翻牌动画期间冻结。
- 轮次指示器（红/黑/当前玩家）单独 OCR/颜色检测；不要只靠棋盘变化推断。
- 计时器 OCR 只在局部 ROI；读不到不影响下棋，但影响超时安全。
- 低置信度格子标 `unknown`；超过阈值暂停，要求用户确认或重新校准。
- 棋盘缩放/窗口缩放后重新计算格点，不要复用旧坐标。

### 9.5 弹窗与自动重启

- 公告、规则、更新、签到、广告、断线、实名、防沉迷：每个维护模板 + 关闭按钮锚点。
- 启动/进入模式时按顺序关闭，最多 3 轮；未知弹窗不要乱点，暂停截图。
- 一局结束：优先点“再来一局”；没有就返回主界面 → 重新点“翻翻棋”。
- 人机练习可以自动连开；真人匹配默认停下，等用户确认。
- 体力/次数限制、广告、实名提示：暂停，不尝试绕过。

### 9.6 权限与运行环境

- 屏幕录制：`CGPreflightScreenCaptureAccess()` / `CGRequestScreenCaptureAccess()`；macOS 15+ 会周期性复查，长期运行要检测授权失效。
- 辅助功能：`AXIsProcessTrustedWithOptions`；用于窗口 raise 和 CGEvent 注入。
- 输入监控：录制人类操作时可能需要 `CGPreflightListenEventAccess()`。
- 游戏窗口必须可见且前台；建议放在独立 Space，用 `IOPMAssertion` 或 `caffeinate` 防止休眠。
- 单实例锁 + 全局急停快捷键，防止两个实例抢鼠标或失控。
- 没有菜单栏 App，急停入口是主窗口按钮 + 全局快捷键；关闭主窗口即退出。

### 9.7 Python 训练进程生命周期

- Swift 用 `Process` 启动 `uv run python -m wgai.cli train --config ... --out ...`，捕获 stdout/stderr。
- `stdout` 逐行输出 JSONL 进度，`stderr` 写日志；`TrainerBridge` 只解析 stdout，避免日志混入。
- 训练完成（exit 0）后，Swift 用 MLX Swift 加载 `models/<version>/`，跑固定输入的 smoke test，再进入评测。
- 取消：`terminate()`，10 秒后 `SIGKILL`；进程退出后清理临时文件。
- Python 崩溃不影响 App：标记 `training failed`，保留旧模型，显示 stderr 摘要。
- 训练和游玩同时跑会争 GPU/统一内存；游玩优先，必要时降低训练进程优先级或暂停训练。
- **不做常驻进程、不做健康检查、不做 act 超时**；训练结束进程即退出。

### 9.8 安全与人工接管

- 单局最长时长、连续失败次数、非法动作次数、匹配超时 → 自动停止。
- 暂停时立即停止注入，把鼠标还给用户；恢复前重新截图确认状态。
- 真人匹配默认不自动连开；检测到对手是真人时，按配置停止或只打一局。
- 不要用固定点击节奏/固定轨迹；加随机间隔和贝塞尔移动，但不要把它当反检测手段。
- 任何异常都保留截图、状态快照和最近 50 条日志。

## 10. 风险与合规

| 风险 | 等级 | 说明 | 缓解 |
|---|:---:|---|---|
| 微信/游戏协议/封号 | 高 | 自动化违反协议；真人匹配/排行榜风险最高 | 自用、低频、人机练习优先、不做分发 |
| 真人对手影响 | 高 | 自动对战可能影响其他玩家体验 | 默认只进人机/练习；真人匹配需显式开启且单局停止 |
| 游戏 UI 改版 | 高 | 入口、棋盘、按钮变化会让脚本失效 | 版本锁定、屏幕分类、重新校准 |
| 棋盘/棋子识别错误 | 中高 | 暗子、皮肤、缩放、动画都会误判 | 格点校准、时序平滑、低置信度暂停 |
| 规则引擎不一致 | 中高 | 模拟器规则与游戏不同，自博弈学错 | 真实回放回归测试、规则版本化 |
| 匹配/弹窗/计时 | 中 | 等待、广告、断线会打断流程 | 超时、模板、暂停、人工接管 |
| MLX Swift 兼容性 | 中 | `mlx-swift` 与 Python MLX 数值可能有差异 | 固定版本、CI 推理一致性测试、模型结构从简 |
| 训练环境 | 中低 | 训练依赖 Python/uv，用户机器可能没有 | 训练按钮禁用并提示；模型可拷贝；不把 Python 打进 App |
| 翻翻棋随机性 | 中 | 暗子随机，短期胜率波动大 | 固定种子、多样本评测、置信区间 |
| 分发 | 中高 | Mac App Store 基本不可行 | Developer ID 签名 + 公证，官网/私下分发 |
| 隐私 | 中 | 录制内容可能包含昵称/头像/聊天信息 | 只存本地、可删除、空间统计 |
| 法律 | 高（分发时） | 对外提供自动化工具风险显著上升 | 仅自用；分发前单独评估 |

> [!danger] 合规底线
> 只做“屏幕 + 输入”的外部自动化，不修改微信/游戏二进制、不读进程内存、不劫持网络。即便如此仍违反微信/游戏用户协议，存在封号风险；对外分发前需单独评估法律风险。**默认只进人机/练习模式，不主动影响真人玩家。**

> [!warning] 2026-10-23 P0-4 实测更新
> 游戏内不存在人机/练习模式，点击“新手场”即进入真人匹配。用户已显式确认：仅自用、允许真人匹配与自动再来一局、无每日局数上限；未知弹窗/匹配超时立即暂停。上表“默认只进人机/练习”的旧假设作废，详见《开发计划》P0-4 与 M0-8。急停、失败截图、异常暂停仍然必须保留。
