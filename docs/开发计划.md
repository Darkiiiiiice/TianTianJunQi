# 开发计划：天天军棋·翻翻棋 AI 客户端

> 依据设计文档《微信小游戏自动游玩客户端》v1（2026-10-23）制定。里程碑周期沿用设计文档第 11 节估算（单人全职总计 10–14 周）。
> 当前工作区状态（2026-10-28）：M0 已跑通；M1-1～M1-9 已完成（校准、格点、样本采集/标注、时序平滑、状态构建、点击执行、屏幕分类、弹窗处理 v1、性能验收），棋盘与屏幕分类器均已接入实时感知；M2 的 Python 规则引擎/模拟器/自博弈与 Swift `EpisodeRecorder` 已完成，下一步人类示范事件采集（M2-8）、关键帧与真实回放回归（M2-6）。

## 1. 总览

```text
P0 前置实测（1–2 天，与 M0 并行）
 └→ M0 骨架与启动闭环（3–5 天）
     └→ M1 棋盘感知与对局操作（1–2 周）
         ├→ M2 数据落盘 + 规则引擎/模拟器（2–3 周，可与 M1 并行）
         │    └→ M3 行为克隆 + MLX Swift 推理 + 评测门禁（2–3 周）
         │         └→ M4 自博弈 + 自动重启 + 打包（2–4 周）
```

- **关键路径**：权限/窗口检测 → 捕获 → 校准 → 棋盘状态构建 → 会话闭环 → 规则引擎 → BC 训练 → 评测门禁 → 自博弈/打包。
- **两大不确定项**：① 游戏内实测信息（入口文案、棋盘规格、人机模式是否存在）；② 规则引擎与游戏规则的一致性。二者任一未确认，对应里程碑不启动。
- **并行策略**：M2 的 `sim/`（纯 Python）与 M1 的感知（纯 Swift）互不依赖，可两人并行或单人交替推进，在 M3 汇合。

### P0 实测结论（2026-10-23 回填）

- **P0-1 窗口**：标题“腾讯天天军棋”，owner `com.tencent.xinWeChat`，横版铺满，`canvasROI` 已回填。
- **P0-2 入口**：主菜单“翻翻棋”艺术字，OCR 关键字“翻棋”可命中。
- **P0-3 棋盘**：截图实测 **5 行 × 12 列 = 60 格**，开局满盘、**30 枚/方**；棋子共 12 类（司令…工兵、地雷、炸弹、军旗），逐类数量与动画时长待清点。
- **P0-4 对手模式**：**没有人机/单机练习**。入口 → 场次选择（新手场/普通场/大师场）→ 点击场次卡立即匹配真人，无二次确认；每局扣 50 金币；结算页“再来一局/切换对手”都会重新进入匹配。**与设计文档默认假设冲突。用户 2026-10-23 显式选择：允许真人匹配、允许自动再来一局、无每日局数上限；未知弹窗/匹配超时立即暂停。**
- **P0-5 规则**：翻旗定阵营 = 连续两次翻到同色棋子；其余移动/吃子/胜负细则仍待回放确认。
- **P0-6 点击注入（2026-10-23 实测）**：
  - `CGEvent.postToPid` 不移动系统指针，但微信小游戏窗口（主进程 + `WeChatAppEx` 渲染进程）均忽略定向事件；公开 API 没有“零指针占用”的可靠点击。
  - 可靠路径 = **AX 把游戏窗口抬到最前 + 目标点在屏幕内 + 全局 HID 点击**；点击后用 `CGWarpMouseCursorPosition` 立即还原指针，实测指针占用约 150ms。
  - 窗口被 Orca/系统设置/钉钉等遮挡时，全局点击会命中遮挡窗口。因此**每次点击前都要重新读窗口 bounds、AX raise，并校验目标点最前窗口**；目标出屏时用 AX 把窗口移回可见区域。
  - **落点坐标不缓存**：绝对屏幕坐标在事件投递前一刻按窗口 ID 重新读取 bounds，再叠加归一化偏移量。这样用户抬窗、等待键鼠空闲期间移动/缩放窗口，点击也不会整体偏移；若最后一刻窗口被遮挡则暂停而不是误点。
  - 小窗口（368×251）下 OCR 会把“翻翻棋”漏识成“翻翻旗”/“翻翻”；**2× 放大**后可稳定命中。主菜单分类另用底部栏“任务/布局/商城/大转盘”兜底。
  - **抓帧画布**：SCStream 默认按小程序**原生画布**输出（实测 461×303 的窗口拿到 1920×1080 帧，游戏只占左上角 928×608，其余全黑）。不裁剪会导致①预览一大片黑区、②**OCR 归一化坐标相对窗口整体偏移、点击落空**。现用 `detectContentRect`（行/列剖面找非黑内容区）裁剪，裁完的帧与窗口一一对应。

**验收**：人工监督下，点击"进入翻翻棋"后客户端自动进入牌局（真人匹配，用户已显式接受自动连开）；日志记录每步耗时；dummy 策略输出合法形状动作；概览页能实时显示竖屏克隆画面；**用户缩放任意尺寸或窗口被其他 App 遮挡后，点击前能自动刷新 bounds、抬窗并还原指针**。

### M1 棋盘感知与对局操作（1–2 周）

目标：**连续 20 次进入牌局；能完成翻牌/落子；感知指标达标。**

> 2026-10-27 进展：M1-3 数据集/模型完成。实测棋盘每方 **25 枚** + 10 个固定空站点（不是 30 枚）；`board-classifier-v2` 用 S3 做 val、S5 做 test，state 430 张 / color 197 张 / piece 197 张，test 三模型均 100%。`make verify-models` 可复现 Core ML 结果。
>
> 2026-10-28 进展：M1-7 屏幕分类器完成。概览页可按 7 类采集屏幕样本（`perception/screen-samples`），`make screen-dataset/screen-train/export-screen/verify-screen` 依次导出、训练、导出 Core ML 并核对；数据集按采集批次（相邻帧间隔 >3s 即分组）切分，棋盘快照并入 `board`。v1 共 320 份样本，val 100%、test 95%（残留混淆：`board→modeLobby`、退出确认弹窗 `popup→matching`，后者已由 OCR 关键字兜底）。`ScreenClassifier` 启动时加载并预热预编译模型，`ScreenStateService` 模型为主、OCR 兜底，概览页显示状态/来源/置信度/推理耗时。
>
> 2026-10-28 进展：M1-8 弹窗处理 v1 完成。新增纯逻辑 `PopupResolver` / `PopupCatalog` / `PopupRoundTracker`：已知模板（退出确认、登录奖励、任务、个人信息、规则、公告、断线重连、广告、实名、更新）按强特征匹配；退出确认只点「取消」，绝不点「确定」；签到/任务/个人信息优先 OCR 关闭字样，其次内置锚点（`popup.close.signIn/task/profile`，校准可覆盖）；规则/公告/断线找不到关闭目标时暂停；广告/实名/更新一律暂停。每次进入流程共享 3 轮关闭预算，超限暂停并截图。未知弹窗导出 `perception/popups/<kind>-时间戳/{frame.png,meta.json,ocr.txt}`，概览页「弹窗处理」行显示结果与截图入口。`ModeEntry` 在初始识别、点击等待、匹配等待和棋盘稳定复核四处统一走弹窗清理；`ScreenStateService` 增加「一键领取/领取破产金/金币不足/恭喜获得/温馨提示」等通用弹窗关键词，避免新弹层被模型误判成结算/牌局。实机已复验：领取救济金弹层 → 未知弹窗暂停并落盘；登录奖励弹层 → 点击 `popup.close.signIn` 关闭后继续流程。退出确认/3 轮上限/规则无关闭目标由单测覆盖，实机复验待补。

> 2026-10-28 进展：M1-9 性能验收完成。`PerfKit` 统一阶段枚举（屏幕 OCR/分类、棋子分类、状态构建、动作决策、点击注入、端到端）、固定容量采样、最近秩 p95、环境快照与应用内报告导出；`ScreenStateService`/`BoardPerceptionService`/`BoardTapService`/`InputInjector` 在真实执行路径打点，概览页新增「性能」行。实时路径把 60 格从 `CGImage` 转为 `CVPixelBuffer` 直通，state 用 batch 推理、color/piece 只对明子批量补跑；`ScreenAnalyzer` 与回放基准共用同一套 OCR/分类/融合。新增 `Tests/PerfBench` 与 `make perf`：回放 30 份棋盘样本（302 份中均匀抽样）端到端 p50 102–105ms / p95 112–147ms（3 次回放，最大 153ms），低于 200ms 门槛；同一批样本棋盘状态准确率 99.4%（1789/1800）、明子颜色/军衔 97.2%（451/464）。20 份屏幕样本分类准确率 80%（v1 模型 95% 留出集，回放样本含少量混淆），OCR p95 约 1.3s 仅作界面切换诊断。测量时系统 load average 约 8–29、swap 占用高，结果偏保守；报告 JSON 写入 `perception/performance/` 并带 `PerfEnvironment`。口径是「帧已就绪 → 点击发出」，不含 0.2s 轮询等待与 3 帧投票的历史积累；动作链路本身已经是稳定棋盘上的增量更新。

## 4. 测试计划（CI 五类，对应设计文档 7.7）

1. **schema 契约**：Swift 编码的 GameState 能被 Python 解码，反之亦然。
2. **规则单测**：军衔/炸弹/地雷/翻牌/移动/胜负 + 真实回放回归；规则改动必须先升 `rules.json` 版本。
3. **过拟合测试**：10 条样本 loss 降到接近 0，证明训练链路未断。
4. **推理一致性**：同一份 safetensors + model.json，Python 与 MLX Swift 输出差 < 1e-4（必须）。
5. **模型加载 smoke test**：App 加载新模型跑 10 步不崩。
6. **Swift 感知内核单测**：格点几何、单应反查、时序平滑、样本导出与标签读写；`make test-swift` 用 swiftc 直接编译纯内核，不依赖 Xcode test target。

节奏：每个里程碑合入前 `make test` 全绿；M2 起规则回归纳入 CI。

## 5. 风险与应对（开发视角）

| 风险 | 应对 |
|---|---|
| P0 实测信息缺失（入口/棋盘/人机模式） | P0 前置为硬门禁；任一项未确认，对应任务不启动 |
| 真人匹配是唯一对手来源 | 每局影响真人玩家与排位，且无练习模式 | 用户已显式接受真人匹配与自动连开；保留急停、未知弹窗/超时暂停、仅自用不分发；继续找好友房/人机入口 |
| 规则引擎与游戏不一致 | M2-6 回放回归是硬门禁；规则版本化，旧模型/数据标 stale |
| 感知准确率不达标 | 校准 + 两级分类 + 时序平滑；低置信度暂停而非硬猜 |
| MLX Swift 数值差异 | 锁定 mlx/mlx-swift 版本 + CI 一致性测试 + 网络结构从简 |
| 训练/游玩争抢 GPU | 游玩优先，训练降级；必要时暂停训练进程 |
| 游戏 UI 改版 | theme/版本检测 → 要求重新校准，禁止硬点 |
| 在线 RL 诱惑 | 严守路线：先 BC + 掩码，模拟器稳定后才自博弈；真实对局只采集不在线学 |
