# 开发计划：天天军棋·翻翻棋 AI 客户端

> 依据设计文档《微信小游戏自动游玩客户端》v1（2026-10-23）制定。里程碑周期沿用设计文档第 11 节估算（单人全职总计 10–14 周）。
> 当前工作区状态：仅 `TianTianJunQi.xcodeproj`（SwiftUI 模板）+ 设计文档，代码从零开始。

## 1. 总览

```text
P0 前置实测（1–2 天，与 M0 并行）
 └→ M0 骨架与启动闭环（3–5 天）
     └→ M1 棋盘感知与对局操作（1–2 周）
         ├→ M2 数据落盘 + 规则引擎/模拟器（2–3 周，可与 M1 并行）
         │    └→ M3 行为克隆 + MLX Swift 推理 + 评测门禁（2–3 周）
         │         └→ M4 自博弈 + 自动重启 + 打包（2–4 周）
```

- **关键路径**：权限/窗口检测 → 捕获 → 校准 → 棋盘状态构建 → 会话闭环 → 规则引擎 → BC 训练 → 评测门禁 → 自博弈/打包。
- **两大不确定项**：① 游戏内实测信息（入口文案、棋盘规格、人机模式是否存在）；② 规则引擎与游戏规则的一致性。二者任一未确认，对应里程碑不启动。
- **并行策略**：M2 的 `sim/`（纯 Python）与 M1 的感知（纯 Swift）互不依赖，可两人并行或单人交替推进，在 M3 汇合。

### P0 实测结论（2026-10-23 回填）

- **P0-1 窗口**：标题“腾讯天天军棋”，owner `com.tencent.xinWeChat`，横版铺满，`canvasROI` 已回填。
- **P0-2 入口**：主菜单“翻翻棋”艺术字，OCR 关键字“翻棋”可命中。
- **P0-3 棋盘**：截图实测 **5 行 × 12 列 = 60 格**，开局满盘、**30 枚/方**；棋子共 12 类（司令…工兵、地雷、炸弹、军旗），逐类数量与动画时长待清点。
- **P0-4 对手模式**：**没有人机/单机练习**。入口 → 场次选择（新手场/普通场/大师场）→ 点击场次卡立即匹配真人，无二次确认；每局扣 50 金币；结算页“再来一局/切换对手”都会重新进入匹配。**与设计文档默认假设冲突。用户 2026-10-23 显式选择：允许真人匹配、允许自动再来一局、无每日局数上限；未知弹窗/匹配超时立即暂停。**
- **P0-5 规则**：翻旗定阵营 = 连续两次翻到同色棋子；其余移动/吃子/胜负细则仍待回放确认。
- **P0-6 点击注入（2026-10-23 实测）**：
  - `CGEvent.postToPid` 不移动系统指针，但微信小游戏窗口（主进程 + `WeChatAppEx` 渲染进程）均忽略定向事件；公开 API 没有“零指针占用”的可靠点击。
  - 可靠路径 = **AX 把游戏窗口抬到最前 + 目标点在屏幕内 + 全局 HID 点击**；点击后用 `CGWarpMouseCursorPosition` 立即还原指针，实测指针占用约 150ms。
  - 窗口被 Orca/系统设置/钉钉等遮挡时，全局点击会命中遮挡窗口。因此**每次点击前都要重新读窗口 bounds、AX raise，并校验目标点最前窗口**；目标出屏时用 AX 把窗口移回可见区域。
  - **落点坐标不缓存**：绝对屏幕坐标在事件投递前一刻按窗口 ID 重新读取 bounds，再叠加归一化偏移量。这样用户抬窗、等待键鼠空闲期间移动/缩放窗口，点击也不会整体偏移；若最后一刻窗口被遮挡则暂停而不是误点。
  - 小窗口（368×251）下 OCR 会把“翻翻棋”漏识成“翻翻旗”/“翻翻”；**2× 放大**后可稳定命中。主菜单分类另用底部栏“任务/布局/商城/大转盘”兜底。
  - **抓帧画布**：SCStream 默认按小程序**原生画布**输出（实测 461×303 的窗口拿到 1920×1080 帧，游戏只占左上角 928×608，其余全黑）。不裁剪会导致①预览一大片黑区、②**OCR 归一化坐标相对窗口整体偏移、点击落空**。现用 `detectContentRect`（行/列剖面找非黑内容区）裁剪，裁完的帧与窗口一一对应。

## 4. 测试计划（CI 五类，对应设计文档 7.7）

1. **schema 契约**：Swift 编码的 GameState 能被 Python 解码，反之亦然。
2. **规则单测**：军衔/炸弹/地雷/翻牌/移动/胜负 + 真实回放回归；规则改动必须先升 `rules.json` 版本。
3. **过拟合测试**：10 条样本 loss 降到接近 0，证明训练链路未断。
4. **推理一致性**：同一份 safetensors + model.json，Python 与 MLX Swift 输出差 < 1e-4（必须）。
5. **模型加载 smoke test**：App 加载新模型跑 10 步不崩。

节奏：每个里程碑合入前 `make test` 全绿；M2 起规则回归纳入 CI。

## 5. 风险与应对（开发视角）

| 风险 | 应对 |
|---|---|
| P0 实测信息缺失（入口/棋盘/人机模式） | P0 前置为硬门禁；任一项未确认，对应任务不启动 |
| 真人匹配是唯一对手来源 | 每局影响真人玩家与排位，且无练习模式 | 用户已显式接受真人匹配与自动连开；保留急停、未知弹窗/超时暂停、仅自用不分发；继续找好友房/人机入口 |
| 规则引擎与游戏不一致 | M2-6 回放回归是硬门禁；规则版本化，旧模型/数据标 stale |
| 感知准确率不达标 | 校准 + 两级分类 + 时序平滑；低置信度暂停而非硬猜 |
| MLX Swift 数值差异 | 锁定 mlx/mlx-swift 版本 + CI 一致性测试 + 网络结构从简 |
| 训练/游玩争抢 GPU | 游玩优先，训练降级；必要时暂停训练进程 |
| 游戏 UI 改版 | theme/版本检测 → 要求重新校准，禁止硬点 |
| 在线 RL 诱惑 | 严守路线：先 BC + 掩码，模拟器稳定后才自博弈；真实对局只采集不在线学 |
